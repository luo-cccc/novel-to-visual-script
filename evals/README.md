# 回归评测

用于维护本技能：改动 `SKILL.md` 或 `references/` 后，用同一批用例重跑，对比改动前后是否更好。执行改编任务时不读取本目录。

## 为什么保留

规则的措辞一改，执行行为就会变。没有固定用例和检查点，改完无法判断是变好还是变差（此前的提交只做措辞精简，无验证手段）。

## 运行方式

每个用例单独开启一个会话，只把 `cases/` 里“给模型的请求”原文发给技能，不附加额外提示。素材按用例如实提供：

- E1–E4、E7、E9、E10 附对应原文或标注的段落；
- E5 的四个子用例各自独立成次，一次只发一条；
- E6 依赖先按 E1（或 E7）跑一次并保存底稿，再把底稿和返修请求一起发出；
- E8 只给用例标注的前半部分，并明确说明后文未提供。

为降低单次波动，每个用例跑 3 次。E5 的四个子用例各跑 3 次，分开记录。

## 判定

- 每个用例的检查点分为 **硬检查点**（不通过即失败）与 **观察项**（记录，不判定失败）。
- 硬检查点全过，该用例记为通过。
- 计分以**子用例**为单位：E1–E4、E6–E10 各 1 个，E5 为 4 个（5a–5d），共 13 个。记录为“通过子用例数 / 13”，并给出每个子用例 3 次的结果分布。E9、E10 为对白与爽点技法新增，旧基线没有这两项，首次运行时同时跑改动前的版本补基线。
- 与改动前的基线对比，出现回退的子用例必须说明原因，不能以“整体感觉更好”结案。

## 记录模板

```text
版本 / 提交：
日期：
E1 通过 3/3  硬失败点：无
E2 通过 2/3  硬失败点：第 2 次答案在 01 场直接报出；回退：否
……
合计：11/13（E5 四个子用例中 5b 失败）
结论与后续：
```

## 注意

- 用例检查点是底线，不是评分表。文本质量仍由人读判断；模拟审读不等于真实受众反馈。
- 公版素材之外的用户素材不要写进本目录。
- 检查点一旦因正当理由调整，要在提交说明里写明；不要为了让改动“通过”而放宽检查点。
